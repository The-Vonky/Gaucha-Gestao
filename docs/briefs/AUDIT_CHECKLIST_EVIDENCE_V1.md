## Outcome and boundaries

Attach images/documents to an individual inspection criterion, list and download them with Audit read access, and logically remove them only while the inspection is editable. Preserve the 158-item catalog, scoring, response semantics and existing Action Plans contract. This document authorizes no production activity; this PR contains documentation only.

## Ownership and storage

- Audit owns `audit.checklist_evidence`, its APIs, UI and helpers in `audit_private`.
- Each row references `(inspection_id, item_key)` in `audit.inspection_answers`; an item key from another template/inspection must fail. Unit derives from the inspection. No sector field: this is a unit-wide resource.
- No dependency on `action_plans.evidence`, its helpers, types or UI internals. No reuse of its bucket. No new universal attachment table, and no Core dependency on Audit.
- Private bucket `audit-checklist-evidence`, created by a future incremental migration. Keys generated by the server: `<inspection_uuid>/<evidence_uuid>`, no user filename or extension. Binary operations use only Supabase Storage API, authenticated user JWT, never SQL writes to `storage.objects` or direct S3/R2.
- Reuse the approved Storage protocol as a specification. Extract a small neutral Shared validator only if concrete reuse warrants it; do not import Action Plans internals.

## Persisted model

| Field | Contract |
| --- | --- |
| id | server UUID primary key |
| inspection_id, item_key | immutable composite answer reference, no cascade deletion |
| object_key | server generated, unique, immutable |
| original_name, content_type, size_bytes | validated, immutable display/type/size metadata |
| status | `pending`, `available`, `removed` only |
| inspection_version_at_begin | server-captured lifecycle version; pending upload cannot survive a finalize/reopen cycle |
| created_by, created_at | authenticated Core profile and server timestamp |
| uploaded_at | confirmation timestamp; absent until confirmed |
| removed_by, removed_at | only present for logically removed evidence |

Constrain pending/available/removed metadata shapes as in Evidence v1. Index answer + status and inspection + live pending/available quota queries. No bytes, signed URLs, duplicated users/units, user-editable actor fields or client-asserted integrity hashes. Rows are append/remove; no evidence editing/version chain.

## Authorization and lifecycle

| Operation | Required scope/capability | Lifecycle |
| --- | --- | --- |
| List, metadata SELECT, sign/download | `audit.inspection.read` on parent unit | available only; draft or finalized |
| Begin, Storage INSERT, confirm, remove | `audit.inspection.edit` on parent unit | draft only |
| Finalize | existing `audit.inspection.finalize` | existing completeness/version rules plus evidence binding below |
| Reopen | existing `audit.inspection.reopen` | existing explicit/versioned transition |

Use Core helpers and Audit revocation-safe authorization patterns. Global and matching unit grants cover the resource; sector-only grants do not. Active session without active profile is denied. Unknown and unauthorized IDs use indistinguishable denial. Write capability does not grant read; the UI requires read to operate the checklist, while mutation RPCs enforce edit independently.

RLS on the exposed evidence table: available rows plus parent read permission; no client INSERT/UPDATE/DELETE grants. Narrow authenticated RPC EXECUTE, fixed empty search paths and qualified relations. Private helper access stays minimal. Bucket-specific INSERT permits only the uploader's live pending key, matching lifecycle version, permission and draft parent. SELECT permits only readable available rows. No UPDATE/DELETE/upsert/move/copy paths for clients.

Finalized inspections allow no evidence mutation. A confirm retry may return success for an already available row after reauthorization, but must change nothing and emit no second event. Removed-row retries are similarly no-ops, never a way to bypass lifecycle checks for a new removal.

## Upload, removal and reopen

Suggested public Audit contracts (names may follow repository conventions; semantics must not change):

1. `begin_checklist_evidence_upload(inspection, item_key, name, MIME, size)` locks inspection, authorizes edit, verifies draft/item/limits, captures current inspection version, creates pending and returns evidence ID/key.
2. Browser uploads using canonical MIME, `upsert:false`, `cacheControl:'0'`. No lock is held during transfer.
3. `confirm_checklist_evidence_upload(evidence_id)` reauthorizes, locks inspection then evidence, requires uploader, unexpired pending, draft and the captured lifecycle version. Verify Storage metadata for bucket/key, owner, exact size/MIME. Mark available and emit one add event.
4. `checklist_evidence(inspection, optional item_key)` returns available rows only, including uploader display name without requiring `admin.user.read`.
5. Sign on click with read permission, 60-second TTL and original download name. Never persist/log URLs. Attachment download only from the API origin; no inline viewer.
6. `remove_checklist_evidence(evidence_id)` checks edit + draft, locks and marks removed, preserving row and object; emits one removal event. Replacement means add new/remove old, never overwrite.

Pending expires after one hour, checked with decision time after lock waits. Retry retains the same evidence ID; Storage “already exists” proceeds to confirm. A lost confirm response is idempotent. Pending/removed are never listed or signed. Failed/expired transfers do not become business evidence.

**Approved reopen policy (E2, 2026-09-29):** retain every existing available file, preserve removed records and audit trail, and permit new uploads/logical removal again with `audit.inspection.edit` after reopen. Reopen alone does not grant edit. A pending upload from before finalization must be rejected even if the inspection has since reopened; begin a new attempt. No automatic restoration of removed files. Re-finalization freezes the then-current available set. Every finalization records the IDs of the evidence available at that moment in lifecycle audit events; physical bytes remain retained. This adds no immutable historical report/revision browser.

Evidence is optional, independent of AT/AP/NAT/NAP/unanswered, and changing a response neither creates nor deletes evidence. Finalization does not wait for pending uploads; it warns the user and confirms only the available set. Pending transfers cannot confirm afterward.

## Concurrency and finalization binding

All evidence mutation lock order: inspection `FOR UPDATE` → caller authorization rows in deterministic order → evidence row. Recheck permission after waits, as in migration 0009. Evidence operations never lock/update an answer or Action Plan. This avoids reversing the existing answer-update path (answer → parent inspection → authorization → Action Plan synchronization).

Evidence changes do not increment inspection/answer versions. Instead, extend the future finalization contract with the **expected available evidence IDs for the entire inspection**, collected independently of the currently displayed section. Under the inspection lock, compare sets atomically before recording finalization. Mismatch returns a visible conflict (`40001`); reload and request review. Empty array is valid, null rejected. Remove the old bypass signature in a new migration and update callers/tests together. No changes to response scoring or completeness semantics.

Consequences to prove with two real sessions: finalize vs confirm/remove cannot silently alter the accepted evidence basis; two begins at quota allow only the remaining slots; two removals emit one event; concurrent uploads use distinct keys; permission revoked while waiting is honored; finalize/reopen cannot revive an older pending upload. A concurrent upload may leave an invisible orphan object; confirmation and reconciliation remain authoritative.

## File rules and known limits

Approved E1 (2026-09-29): evidence is optional; maximum 10 MiB/file (1–10,485,760 bytes), **10 active files per criterion and 100 per inspection**. Both counts include available + non-expired pending, exclude removed/expired, and are enforced together under the inspection lock. Inspection quota bounds a 158-criterion audit to 1,000 MiB of active files; removed bytes still consume storage. These approved Audit quotas do not change the separate 20-per-plan limit.

| Extensions | Canonical MIME | Client signature check |
| --- | --- | --- |
| jpg/jpeg | image/jpeg | FF D8 FF |
| png | image/png | 89 50 4E 47 0D 0A 1A 0A |
| pdf | application/pdf | %PDF- in first 1024 bytes |
| xlsx | application/vnd.openxmlformats-officedocument.spreadsheetml.sheet | ZIP 50 4B 03 04 |
| docx | application/vnd.openxmlformats-officedocument.wordprocessingml.document | ZIP 50 4B 03 04 |

RPC enforces allowlist, extension↔canonical MIME and size; bucket enforces MIME/size; confirmation verifies stored metadata. Client derives canonical MIME from allowed extension and checks bytes, not `File.type` alone. Apply Evidence v1 filename rules: NFC basename, 1–180 characters, no separators/control/bidi characters, forbidden punctuation, leading dot or trailing dot/space. Render names as escaped text.

**Approved E3 residual-risk acceptance for v1 (2026-09-29):** these client magic-byte checks can be bypassed. ZIP signature cannot distinguish XLSX/DOCX/macros/arbitrary ZIP content. There is no trusted byte parser or antivirus in the existing platform flow. Files remain untrusted content: do not claim they are safe, antivirus-scanned, sanitized or server-validated. The approved v1 decision explicitly accepts client-only byte validation and preservation of EXIF, only with authenticated/scoped/audited uploaders, attachment-only download, API origin isolation, canonical non-active MIME, no preview, production nosniff/no-cache gates and endpoint protection. Preserve original bytes; do not extract EXIF/GPS, but warn that originals may contain it. Trusted validation/quarantine remains a separate future evolution, outside v1; never silently introduce a new compute service. File types, size, MIME and extension restrictions remain mandatory.

Reject all other extensions/MIMEs, including HEIC, SVG/HTML/scripts/executables, legacy Office and macro extensions. Browser rejection is not a security guarantee against renamed content.

## Audit and recovery

Trusted `core.system_audit_log` events use module `audit`, entity `checklist_evidence`, parent unit and inspection/item IDs: add at successful confirm, logical remove, authorized operator purge. Safe before/after metadata excludes bytes, object keys, URLs, tokens and credentials. Begin/failed operations/idempotent repeats produce no business event. Finalize events include frozen evidence IDs; reopen records transition without deleting that history.

Private reconciliation reports expired pending (object present/absent), available missing Storage metadata, and objects with no evidence row. Operators additionally verify object bytes through Storage; SQL metadata alone cannot prove object existence in the backend. No automatic purge or schedule in this implementation.

Backup includes Audit evidence metadata, Core audit history, Storage metadata and independent object copies. Restore DB to T, restore objects from a copy at/after T, reconcile, then exercise authorized downloads and cross-unit denial in an isolated environment. Copies must retain any objects purged after T until the database recovery window expires; “copy at/after T” alone is insufficient after physical deletion. No retention interval is invented here. Purge requires recorded human authorization, Storage API deletion and audit event; never SQL deletion of Storage rows.

Production gates remain separate: independent/access-separated backup, measured RPO/RTO and retention, tested restore with actual downloads, nosniff and cache behavior, reconciliation monitoring, purge runbook. This brief implements none of the production infrastructure.
